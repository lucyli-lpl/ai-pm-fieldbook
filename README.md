# AI PM Fieldbook · 企业级 AI 产品能力边界方法论

> 一线实践复盘，一点一点写下来的东西。不是理论教程，是一个企业 AI PM 在真实项目里踩过、总结过、反复校正过的工作方法。

**一句话内核：能力三区不是难度分级，而是三种产品承诺——核心区保证结果，边缘区保证处理，界外区保证边界。**

---

## 这套方法论适合谁

这是一套基于企业级 AI 项目经验总结沉淀的方法论，适用于有明确规则、流程约束的企业 AI 应用的 **0-1 阶段**。

**如果你在做个人项目的 vibecoding，或只是快速验证一个 demo——这不适合你，别用。** 它会拖慢你。

**但如果你在做一个"错了会出事、要对上线负责"的企业 AI 应用，它能帮你少走弯路。** 尤其是这种处境：当你无法一个人全栈搞定，也没有一个能快速迭代的 AI 小组，而是身处一个分工明确的团队里——UI 设计、前端、测试、运营各在一环，彼此之间充满协作摩擦——那么本方法论在每个节点上对"交付材料"的要求（能力边界母表、验收规范表、badcase 分类体系……），会成为你穿透这些摩擦、让整个团队按同一套标准协同的公共语言。

在没有摩擦的环境里，这些交付物是冗余；在充满摩擦的环境里，它们是润滑剂。这套方法论看起来"重"，是因为它默认了：你没法靠拍肩膀和同事对齐，你得靠文档。这恰恰是绝大多数企业 AI PM 的真实处境。

---

## 它解决什么问题

传统软件的能力是确定的（点按钮就跳页）；AI 的能力是模糊的、有边界的、会在边缘失效的。所以 AI 产品最该被精确规定的，不是"有哪些功能"，而是：

- 能力边界在哪（核心 / 边缘 / 界外）？
- 每个区域该表现成什么样？
- 什么算达标、什么算越界？
- 失败了怎么归因、怎么改进？

**这套方法论的核心工作，就是把"模型的模糊能力"，规定成"清晰的产品承诺"。** 它给你一套从立项、测试、上线到运营的完整判断框架，让这件最难、最核心的事有章可循。

## 从哪读起

不用从头啃到尾。按你当前所在的阶段，直接跳到对应章节：

| 你正在做什么 | 读这些 |
|---|---|
| **刚立项，要定产品边界** | 第一章（核心内核）+ 第六章（AI 产品观）——先建立"三区=三种承诺"的判断框架 |
| **判区遇到复杂场景卡住** | 第二章（复杂场景如何判区）+ 第三章（通用场景特征库） |
| **要准备测试 / 写验收标准** | 5.1 测试（四层结构、S0/S1/S2 × L1/L2/L3、验收规范表） |
| **上线了，要做数据运营 / badcase 分析** | 5.2 数据运营（五步闭环、error analysis、归因派单） |
| **要给技术把关 prompt / 设计 skill** | 5.3 生成把关（prompt 阶梯、system prompt vs skill 分层） |
| **要选架构 / 定护栏** | 5.4 架构选择（CoT/workflow/agent）+ 5.5 生产护栏与可靠性 |

**第一次读，建议至少读完第一章和第六章**——它们是地基，其余都建立在"能力三区"这个判断框架之上。

## 关于文中的示例

本方法论用两个**虚构的参照产品**贯穿全文举例，方便把抽象方法论落到具体场景：

- **服务台助手**：一个企业内部的 IT 服务台 AI 助手，员工向它查询流程（"重置密码走什么流程"）、检索文档、匹配支持工程师、发起工单。属"检索问答 + 轻操作型"。
- **报销助手**：一个报销工作流 AI 助手，帮员工查询进度、填单、提交。属"任务型 / 带工作流型"。

这两个产品是示例载体，不指向任何真实产品。方法论本身脱胎于作者在多个真实企业级 AI agent 项目中的实践与迭代（见正文末尾的成长记录，v1 → v2.1 的每一步校正都有据可查）；示例已做通用化处理，以便你迁移到自己的产品上。

## 状态与迭代

这是一份**活的文档**。它从 v1 迭代到 v2.1，每一版都是在真实项目里遇到问题、回来校正的结果。方法论中多处标注"实践假说待验证"——这是刻意保留的诚实：AI 产品方法论这个领域还很年轻，与其假装完备，不如如实标注边界，随实践持续进化。

如果你在自己的项目里用了它、发现了它讲不通或没覆盖的地方，欢迎提 issue——那正是下一版校正的起点。
