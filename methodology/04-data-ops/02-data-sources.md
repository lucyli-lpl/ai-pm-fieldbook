## 三源分工（互补，覆盖不同盲区）

| 数据源 | 采什么 | 覆盖谁 |
|---|---|---|
| 点踩（用户主动反馈） | 用户明确的不满 + 原因选项 | 愿意开口的用户 |
| 埋点（用户行为） | 客观行为（点击、放弃、重新生成…） | 全量用户（含沉默的） |
| 后台打标（归因分类） | 给数据贴母表维度的标签 | —（是加工，非采集） |

> 系统主动信号（后台算，非用户动作触发）是运营主力，因为它覆盖沉默用户：兜底触发率、追问率、多轮未解决率、同问题复现率、行为/结果信号。

## 三源关联：用 canonical feedback event 把三源钉在一起

- **不是三张表硬拼，而是设计一个统一的「反馈事件」结构**；
- **关联键 = trace_id / conversation_id**：每个反馈事件都挂上对话标识符；
- **保留原始文本 + 出处（provenance），schema 支持「再处理」**：母表和打标器会演变，原始数据完整保留，母表升级后能拿旧数据用新分类重跑。**只存"打好的标"不够，必须存原始对话。**

## 点踩选项设计原则

- **选项映射内部归因**：每个口语选项背后挂一个内部标签，映射到母表的失败类型/归因维度。
- **让用户按「现象」选，而非「技术归因」选**：用户能准确感知"答错了/页面卡了"，但难准确区分"失忆 vs 一开始就没懂"。
- **点踩与原因拆成两个独立事件、不选原因也算点踩**：先保召回，再补精度。
- **留"其他 + 自由输入"**：捞母表没预料的新失败类型。
- **万金油选项（如"没有帮助"）应去掉**：它无法反解到任何具体失败，制造脏数据。
- **不做「点踩后追问」**：点踩时用户耐心已降，追问惹反感。

## 后台打标方案

打标 = 给每条 badcase 贴母表维度的标签。**母表就是打标字典**。

**三维打标：**

| 维度 | 取值 | 用途 |
|---|---|---|
| 失败层级（严重度） | S0 / S1 / S2 | 优先级、是否阻断 |
| 归因 | 路由意图 / 知识库 / 生成 / 系统前端 / 轻操作执行 | **决定派给谁修**（最关键） |
| 场景 | 母表编号 | 定位母表哪行、反哺 |

**打标器（分类器）必须版本化**：改了打标器的 prompt/逻辑，会让某类 badcase 统计假性波动——你以为"产品变差了"，其实是"标尺变敏感了"。
