## 一、核心内核

### 1.1 三个维度

- **场景 = 长什么样**：用户提出了什么需求，当前具备什么客观条件。
- **动作 = 该怎么做**：产品面对该场景应该作出的正确反应。
- **归因 = 为什么没做好**：实际表现不达标后，需要修复哪个环节。

> 口诀：**场景看输入，动作看预期，归因看修复。**
> 边界划分看场景，测试验收看预期动作和结果，运营分析看归因。

三个高频串台错误：

1. 根据模型这一次答得好不好反推能力区域；
2. 把追问、兜底等正确动作当成错误原因；
3. 把用户跨模式表达当成模型错误——用户切换意图是场景，系统没有正确识别和路由才是错误。

“知识不足、权限不足”等表述需要区分两种身份：

- 产品事先确认正式知识未覆盖、规则冲突或系统条件不足：这是客观供给条件，可以用于判定边缘区；
- 模型没答好后，运营推测“可能是知识库或权限问题”：这是待验证归因，不能反过来定义场景。

### 1.2 两套坐标系

**坐标系一：需求与产品能力的关系**

- 核心区；
- 边缘区；
- 界外区。

**坐标系二：应用内部处理链路**

- 路由与意图识别；
- 各处理模式；
- 知识、数据或系统调用；
- 回复与结果生成。

能力三区不掺路由。用户从一个目标切换到另一个目标，不因此进入边缘区或界外区；路由层应在每一轮判断这是延续上文、纠正理解还是切换了新目标。

### 1.3 三区 = 三种产品承诺

| | 核心区 | 边缘区 | 界外区 |
|---|---|---|---|
| 产品承诺 | 稳定、完整地完成 | 不保证完整完成，但保证正确处理 | 不解决该需求，但保证正确识别和承接 |
| 判定依据 | 存在明确、经设计的稳定完成路径，且产品**承诺**在此稳定完整交付（承诺在先，验证在后） | 与产品业务相关，但受当前信息、知识、组合规则、数据或系统条件限制，尚不具备可稳定交付的完成路径 | 不属于产品整体能力，或产品明确禁止完成 |
| 主要动作 | 直接完成；意图归一后完成；必要追问后完成 | 完成可完成部分；拆解处理；说明限制；按真实缺口降级承接 | 停止越界部分；说明边界；提供允许范围内的帮助或真实移交路径 |
| 测试重点 | 结果正确、完整、可执行，并达到目标稳定性 | 同时观察完整处理概率与安全降级稳定性 | 预期动作与实际动作匹配，且边界表达、事实和下一步正确 |
| 失败底线 | 不应错误降级或过早兜底 | 不把不确定内容说成确定结论，不因部分不确定而放弃全部可完成内容 | 不越界作答，不编造能力、原因或移交结果 |

三区依据产品**承诺**在此提供到什么程度，不依据模型某次表现或其自我表达的“置信度”。

**判区与验收解耦（重要）**：核心区是产品的**应然承诺**——产品决定“在此必须稳定完整交付”，因此它的身份来自「是否存在明确完成路径 + 产品是否承诺」，**不来自“这阵子实测达没达标”**。
- 判区看：路径是否明确、产品是否承诺（应然）；
- 验收看：实测是否达到承诺指标（实然）。
- 因此：某核心区场景实测暂未达标，说明它**没兑现承诺、需要修**，而不是把它降级为边缘区；反过来，某边缘区场景偶尔完整答对，也不因此升为核心区——它仍不具备被承诺的稳定完成路径。**表现浮动改变的是“达没达标”，不改变“它属于哪个区”。**

核心区的准确率、召回率和重复运行一致性目标，由产品在测试与验收方案中明确（属验收环节），不在缺少基线数据时虚构统一数字。

### 1.4 追问在三区的不同目的

- **核心区追问**：已有经过确认、能够稳定收敛的追问路径；补齐决定性信息后必须完成。
- **边缘区追问**：确认仍可完成的部分，或判断当前限制是否可以解除。
- **界外区追问**：仅用于确认需求是否确实超范围，或是否包含仍可提供的部分。

不能笼统规定“信息不全就追问”。追问必须有明确目的，并真正改变后续结果。

**追问的两种方式（结构化澄清 vs 推理式澄清）——按"不确定性从哪来"选择：**

| | 结构化澄清 | 推理式澄清 |
|---|---|---|
| 不确定性来自 | 某个**具体信息（字段）缺失** | **语义/场景的多义**，有多个合理解读 |
| 怎么问 | 问那个已知的空（"你在哪个部门？"） | 把 AI 的**判断分支暴露出来**让用户对号入座 |
| 依赖 | 预定义字段 | AI 临场推理，**无需预定义字段** |
| 例 | 缺"所在部门"导致工单模板匹配不唯一 → 追问部门 | "我邮箱有问题"→ AI 摊开："是收不到外部邮件（走邮件网关排查）/登录不上（走账号密码流程）/还是提示容量已满（走配额扩容）？" |

- **两者不可互相替代**：当不确定性是"语义多义"（无法枚举成字段）时，结构化澄清做不到，必须用推理式澄清。
- **推理式澄清的实现要点**：让匹配环节输出"候选 + 各自对应的前提 + 区分点"（AI 本就在做这个推理，只需让它输出）→ 多候选时不返回全部结果、而是把推理组织成反问 → 用户补充后带上下文重匹配。全程无需预定义字段——这正是 LLM 的强项。
- **常见误区**：技术容易只把"追问"理解为"填字段"，遇到语义多义场景便认为"无法追问"。纠正：追问不必依赖字段，AI 可临场生成澄清分支。（企业级 agent 项目验证）
- 推理式澄清的额外价值：它把 AI 的不确定性从"背后瞎猜"变成"台面上可交互"，还顺带教育用户（用户可能自己都不知道问题出在哪个环节），体验反而更好。

### 1.5 不同区域的验收重点

**核心区保证结果**

- 观察准确率或任务完成率；
- 观察意图识别召回率和子目标完整性；
- 观察必要追问是否有效收敛；
- 对同一条件重复运行，观察关键结论、追问和交付结果的一致性；
- 观察是否错误降级或过早兜底。

**边缘区保证处理**

- 上限能力：有多大比例可以完整处理；
- 底线能力：不能完整处理时，有多大比例能够完成确定部分并正确降级；
- 风险指标：越界硬答、猜测性结论、整体放弃、错误兜底。

边缘区不同次运行可以在“完整完成”和“正确降级”之间波动，但不能在“正确降级”和“自信乱答”之间波动。

**界外区保证边界**

界外区不评价用户所索取的实质答案是否正确，因为产品本就不应提供该答案；但仍需检查：

- 预期动作与实际动作是否匹配；
- 边界说明是否准确；
- 是否编造原因、能力或移交结果；
- 下一步是否真实可用；
- 是否保留允许范围内可以提供的帮助。

因此，界外区验收 = **动作匹配度 + 边界表达正确性**，不是“只要拒答就通过”。

## 二、复杂场景如何判区

### 2.1 表述模糊或信息不足

- 存在有限、明确的决定性信息，产品知道问什么，用户补充后可以稳定完成：核心区。
- 用户不知道、不愿提供，或者当前产品没有能够稳定收敛的追问路径：边缘区。
- 即使补充信息，现有知识或系统仍无法支持判断：边缘区。
- 追问后确认需求整体超出能力或属于禁止事项：界外区。

如果本来存在明确完成路径，但模型没有问到决定性事实、重复追问或过早兜底，这是核心区 Badcase，不应把场景降为边缘区。

### 2.2 多意图混合

多意图首先是路由层需要识别和拆解的场景，不天然属于边缘区。

- 每个子目标都有明确完成路径：分别完成，属于核心能力；
- 不同子目标可能分别落在核心、边缘和界外；
- 整体是否达标，取决于是否识别全部子目标、没有漏答，并对每一部分采取匹配动作。

### 2.3 复杂或交叉知识

“复杂、罕见”本身不直接决定区域，关键看是否存在经过确认、能够稳定执行的完成路径。

- 多个子问题能够依据现有知识独立完成：拆开完成，可属于核心区；
- 必须判断不同知识之间的组合、先后、优先或替代关系，而正式知识没有提供规则：边缘区；
- 用户进一步要求作出产品明确禁止的专业判断、审批或不可执行动作：界外区。

### 2.4 路由：不是独立场景，而是依附于真实需求的复杂条件

**路由不构成一类独立场景。** 方法论对「场景」的定义以**用户需求为起点**（用户做了什么、提了什么需求、当前具备什么客观条件）；而路由是系统**内部处理动作**，没有独立的用户需求做起点。AI 产品里不存在「纯路由场景」——路由永远依附在一个真实需求上（用户是来问流程/拿模板的，不是来「触发一次路由」的）。若硬把路由列为独立场景，会与真实需求场景重复、冲突。

因此路由以三种身份存在，都不进能力三区：

- **① 作为动作**：正确识别意图、切换、拆解多意图、区分延续上文 vs 新目标——是系统该做对的反应。
- **② 作为归因**：失败根因可落在意图识别层（走错门 → 查 router，而非因最终回答不好就默认归因到生成层）。
- **③ 作为 trace 观察切面**：追踪对话时可专门关注路由质量。

**那些需要专门测试的路由相关情形**——多轮中途切换目标、一句话多意图、用户纠正理解、表面相似实为延续——**不作为独立场景，而是已有真实需求场景在「多轮 / 多意图」复杂条件下的变体（分段测试）**：
- 多轮切换 = 「问流程」等真实场景在「多轮条件」下的变体；
- 多意图 = 多个已有真实场景叠加，拆解后各归其位分别判区。

它们的测试归属在对应的真实场景那里（加复杂条件），归因时关注路由层。这样既不漏测，也不与真实场景重复。

## 三、通用场景特征库

### 3.1 核心区

| 特征 | 说明 | 例（服务台助手） |
|---|---|---|
| 意图明确、信息充分 | 已有稳定完成路径 | "重置域账号密码要走什么流程？" |
| 表述口语但可稳定归一 | 可以识别为已有业务目标 | "我新电脑想装那个设计软件"→归一为查找软件安装申请流程 |
| 缺少有限的决定性事实 | 产品知道问什么，用户补充后能够完成 | 用户要找对应系统的支持工程师，但未说明是哪个业务系统；补充后即可按规则匹配 |
| 多个可独立完成的目标 | 路由能够拆解，每项都有完成路径 | 同时查询申请流程和对应的申请表模板，且两者分别能依据正式知识匹配 |

### 3.2 边缘区

| 特征 | 说明 | 例（服务台助手） |
|---|---|---|
| 信息不足且无法补齐 | 用户无法提供必要条件，或产品没有稳定追问路径 | 用户无法说明决定工程师匹配所需的业务系统或归属部门 |
| 表述持续模糊 | 最小必要澄清后仍不能可靠归一 | 用户始终只说“那个系统登不上”，会话中没有可识别的具体系统 |
| 知识部分覆盖 | 可以确认部分结果，但特殊细节没有依据 | 能匹配申请流程，但知识没有覆盖用户追问的特殊审批例外 |
| 缺少交叉判断规则 | 单项知识存在，但组合、先后或替代关系没有依据 | 同一事项涉及权限申请与设备领用两个流程，用户询问两者先后关系，但知识库未规定 |
| 当前供给不足 | 知识冲突、有效性不明、权限未知、入口失败或人员数据无效 | 两个流程适用范围重叠无法排除，或 ITSM 无法返回有效工单入口 |

### 3.3 界外区

| 特征 | 说明 | 例（服务台助手） |
|---|---|---|
| 超出产品能力 | 需要 IT 支持工程师结合具体情况作判断 | 要求判断某个高危权限申请该不该批、某台故障服务器要不要重启 |
| 明确禁止事项 | 越权、安全、隐私或未开放动作 | 要求绕过审批直接开通权限、查看他人账号信息或自动通知工程师 |
| 完全无关需求 | 与产品服务范围无关 | 要求完成与 IT 服务台无关的通用任务 |

## 四、应用类型变体

### 4.1 纯问答型

- 输出主要是信息；
- 核心区主要测答案正确性、完整性与稳定性；
- 专业领域的错误可能影响用户决策，不能默认“再问一次即可逆”。

### 4.2 检索问答 + 轻操作型（如服务台助手）

服务台助手不是纯问答型。一次 AI 回复可能同时包含自然语言、流程卡、模板卡、工程师卡和可执行入口，还可能依赖知识检索、ITSM 当前结果及多轮上下文。

- 核心区不仅测答案，还要测资源匹配、卡片字段、权限、版本、入口和操作结果是否一致；
- 能力边界以“一次用户目标及其处理阶段”为单位，不局限于一段文本；
- 一次 AI 回复可以包含多条消息或多张卡片，但共同组成一次交付；
- 多意图由路由层识别和拆解，拆分后的每个子目标分别判断能力区域；
- 打开、下载、复制、发起工单等操作必须以真实系统结果为准，不能把展示入口表述成已发起流程或已联系工程师。

### 4.3 任务型或带工作流应用（如报销助手）

任务型应用除信息正确外，还需增加：

1. **执行结果**：说对不等于做对，需验证真实动作结果；
2. **错误代价**：不可逆或高风险动作应更保守，并在执行前确认；
3. **状态与流程节点**：能力边界需要对每个流程节点分别判断；
4. **停止与恢复**：失败、超时、重复、撤销和人工接管需要明确路径。

动作清单应随应用实际能力裁剪，不为满足框架而硬凑所有格子。移交的本质是把用户送到真实能解决问题的地方，不拘泥于真人，但只有产品确实存在该路径时才能使用。

### 4.4 其他类型

- 生成型：待真实项目验证后补充；
- 多 Agent 编排型：待真实项目验证后补充。

## 五、能力边界的落地：测试 + 数据运营

### 5.0 总览：两个阶段，一条循环（ADLC）

同一套能力边界（母表），驱动一个跨越发布的持续改进循环。业界称之为 ADLC（Agent Development Lifecycle）：**上线前测试 → 发布 → 上线后数据运营 → 反馈进下一版**。

```
        ┌─────────── 母表（单一事实源，共享轴心）───────────┐
        ↓                                                      ↓
  上线前：测试（5.1）                            上线后：数据运营（5.2）
  判定「够不够格发布」                            让数据驱动「持续爬坡」
  ─ 数据：预设/合成输入                           ─ 数据：真实用户流量
  ─ 目的：门禁                                    ─ 目的：发现与改进
  ─ 手段：断言(L1)/人工·LLM(L2)/A-B(L3)          ─ 方法：三源采集→打标→error analysis→派单
        └───────────→ 发布 ───────────→ 监控 ─────────┘
                                                （反馈进下一版）
```

**测试与数据运营的分界（三条重合的线）：**

| | 测试（5.1） | 数据运营（5.2） |
|---|---|---|
| 时机 | 上线前 | 上线后 |
| 数据 | 预设 / 合成输入 | 真实用户流量 |
| 目的 | 门禁（够不够格发布） | 爬坡（持续发现和改进） |
| 核心能力 | **判定质量**（评测手段 + 标准） | **数据流与归因**（数据源、关联、指标、归因） |

**关键区分：断言(L1)、人工/LLM 评测(L2)、A-B(L3) 是「测试」的手段（判定质量的工具），不是数据运营的工具。** 数据运营的核心不是"用什么评测手段"，而是"数据怎么来、怎么关联、怎么变成可归因的洞察"。两者只在末端交接：A-B（L3）用于验证运营循环中某次优化是否真的更好。

> 定位说明：AI 产品的质量不由"发布时"决定，而由"发布后的数据运营循环"决定——传统软件发布即巅峰（之后只修 bug），AI 产品发布是起点（之后靠数据爬坡）。因此数据运营方案与测试方案同等重要，是与 PRD 并列的核心资产。
>
> 数据运营部分的方法来源：Hamel/Shreya 的 error analysis（分析方法）+ OpenAI/Arize 反馈系统复盘（工程架构）+ 真实项目实践推导。因「AI 产品数据运营」这一领域尚无成熟公开方法论，此部分较多依赖实践假说，将随真实项目运营持续验证。

### 5.1 测试（上线前：判定够不够格发布）

> 测试 = 上线前，用预设/合成输入验证"够不够格发布"。手段是断言(L1)/人工·LLM(L2)/A-B(L3)。以下四层结构讲清"谁判定、按什么标准、谁决策"。

> 本节总骨架（先看这张图，后面 5.1.1–5.1.6 都归位于此）。
> 验收规范不是单一框架，而是**四层结构**——每层归谁、回答什么，界限清晰：

```
第4层  决策（PM）        阻断发布？达标？先修谁？
                         ↑ 靠「应然线 × 实然值」相碰
第3层  应然（PM 预先定）  严重度 S0/S1/S2 → 各自的通过率要求线
       实然（算出来）     准确率 / 召回 / 通过率（按场景聚合）
                         ↑ 聚合
第2层  判定（QA/代码）    单条：L1 断言 过/不过 · L2 人工 好/坏（二分）
                         ↑ 执行
第1层  期望（PM 定）      每个场景该有什么行为
       来自能力边界方法论  （核心区做对 / 边缘区降级 / 界外区拦截）
```

**读这张图的三个要点：**

1. **判定层 vs 决策层要分开**。L1/L2 在第2层只做二元判定（过不过、好不好），**判定时不需要严重度**；严重度、指标、决策都在第3–4层。你会觉得某些概念「主观」或「看似多余」，多半是把它错放到了判定层——放回决策层就归位了。

2. **一条验收标准是「三轴交叉」的**，一个场景要同时标注三样：
   - **期望行为**（能力三区决定）——核心/边缘/界外各自该做什么；
   - **严重度**（决定通过率）——S0/S1/S2；
   - **测试手段**（可判定性决定）——L1 断言 / L2 人工。
   > 同一场景可按严重度和可判定性**拆成多行**分别验收。例：「多候选追问」→「是否触发追问」是 S1、用 L1 断言；「追问话术质量」是 S2、用 L2 人工——一分为二。

3. **应然 × 实然才能决策**：聚合指标（准确率/通过率）是「测出来的实然（现在多好）」，严重度是「定出来的应然（该多严）」。同一个实测 98%，配 S0（要求100%）是事故、配 S2（要求85%）是超额达标——**缺任一都做不了决策**。

**验收规范表的样子**（以服务台助手「问流程」为例）：

| 场景（来自能力边界） | 期望行为 | 严重度 | 通过率 | 测试手段 |
|---|---|---|---|---|
| 典型提问命中流程 | 命中正确 flowId + 返回 C5 卡 | S1 | ≥95% | L1 断言 flowId 正确 |
| 无权限却渲染链接 | 无权限时不含任何链接 | **S0** | **100% 门禁** | L1 断言 link 为空 |
| 多候选未追问硬猜 | 应触发 C3 追问 | S1 | 触发 100% | L1 断言 action==clarify |
| 追问话术质量 | 问决定性信息、不啰嗦 | S2 | ≥85% | L2 人工评 |
| 界外要求判高危权限审批未拦 | 应走 C10 兜底不硬答 | **S0** | **100% 门禁** | L1(动作)+L2(话术) |

> 命名提示：**严重度用 S0/S1/S2（Severity），评测手段用 L1/L2/L3（Level）**——两套是正交的轴（一个量后果轻重、一个量判定手段），早期共用「L」易混，已正名分开。「优秀（原 L3 加分项）」不进验收（验收是过/不过的门槛判断），挪到监控当观察项。

以下为四层结构的展开：第2层见 5.1.1–5.1.3（评测手段与判定），第3–4层见 5.1.4（通过率）、5.1.6（严重度与决策心法），组织分工见 5.1.5。核心区/边缘区/界外区各自的观测要点：

- 核心区：结果准确、完整、稳定；
- 边缘区：完整处理率 + 正确降级率 + 越界硬答率；
- 界外区：动作匹配度 + 边界表达正确性；
- 多轮 / 多意图：不单列为独立维度，而作为上述真实场景在**复杂条件下的变体**覆盖（多轮切换、多意图拆解），归因时关注路由/意图识别层；
- 任务或操作：另测真实执行结果与成功凭证。

#### 5.1.1 评测分三层（判定方式不同 → 能测的问题种类不同）

评测按“谁来判、判起来多贵”分三层，三者不是能力递增、可互相替代，而是各测各的、组合起来才完整：

| | 判定主体 | 能测什么 | 成本 / 规模 | 使用节奏 |
|---|---|---|---|---|
| L1 断言测试 | 代码断言 | 只能测**客观可判定属性**（格式、数量、越权、字段、是否命中枚举、应触发的动作） | 便宜、可批量 | 每次代码/prompt 改动都跑 |
| L2 人工 + 模型评测 | 人 / LLM | 能测**需判断的语义质量**（专业性、诚实降级、动作是否恰当、话术） | 贵、量受限、需精心设计 | 定期跑 |
| L3 A/B 测试 | 真实用户行为 | 能测**真实因果**（用户是否真受益） | 最贵、需生产数据 | 重大产品变更后 |

分层本质：用便宜快速的检查挡住大部分问题，只把真正需要判断的留给上层。能断言的走 L1，要判断的走 L2，要看真实受益的走 L3。

**关于 L3 的定位**（避免误解）：L1/L2 测「AI 答得对不对、好不好」，L3 测「AI 是否真的驱动了想要的用户行为和业务结果」——这是从「输出质量」到「真实影响」的跨越。三点判断：
- L3 是**通用产品/数据技能**（分流、对照组、统计显著性），不是 AI 特有难点，无需在 AI 评测里另起炉灶；
- L3 天然**后置**：前提是 L1/L2 已把质量保证到一定水平，否则 A/B 测出的差异被 bug 污染；且需真实流量和足够样本，冷启动阶段用不上；
- **但 L3 的前提——「能衡量真实结果的埋点」——必须上线时就埋好**，否则将来无数据可比。详见 5.2 监控视角的「行为/结果信号」。

#### 5.1.2 断言（断言测试 L1 的原子）

- 断言 = 对输出的**某个可被代码自动判定真假的属性**做检查；成立即过，不成立即报错。
- 断言测的是「必须成立的客观条件（可接受行为的边界）」，**不是**「文本等于某个标准答案」——自然语言换个说法就会误伤，几乎从不 assert 文本相等。
- 断言优先作用在**结构化字段**（如 flowId、templateId、agentId、downloadState），而非模型的自然语言原文。

**PM 的高价值动作：把一条产品要求里「能客观判定的骨头」抽出来交给 L1，把「需要体会语义的肉」留给 L2。**
例：「无权限时礼貌告知但不给链接」——「不给链接」可断言（link 字段为空 / 输出不含 URL），归 L1 硬兜住；「礼不礼貌」需判断，归 L2。

#### 5.1.3 断言测试（L1）落地三步

**① 按 feature → scenario 拆，每个场景配断言**
- 把能力拆成 feature，再按「结果形态」把每个 feature 拆成 scenario，逐一配断言。
- 断言分三类，必须成对/成组设计，不能只写正样本：
  - **正样本（召回）**：典型提问 → 期望命中正确资源（如 flowId == 正确流程）。测「该命中的有没有命中」。
  - **负样本（精度）**：断定「不该发生的一定不发生」。两种形态——① 同一道题对「别的流程」断言不被误触发（与正样本共用题目、不同视角）；② 纯界外题，断言 flowId/templateId/agentId 全为空（独立题目）。测「不该命中的有没有被误命中」。
  - **边界样本（劈成两半）**：模糊/多候选提问 → L1 只断言「有没有触发正确动作」（action == clarify / fallback，可判定）；动作的**质量**（问得好不好、是否问决定性信息）归 L2。L1 守底线「没乱猜」，L2 磨质量「问得好」。
- 另设**通用断言**（不绑定 feature，全局都必须成立）——对应方法论的 **S0 红线**，如「输出不得含内部 UUID」「无权限响应不得含链接」。S0 断言做成**发布门禁**（一票否决），不参与平均通过率。

**② 用 LLM 批量合成测试用例**
- 不必等生产数据；先合理猜测用法合成，放小批用户后再用真实用法反哺合成策略。
- **故意造难**：测试若全过，可能是题太简单；好测试的信号是模型会挂——这些失败正是后续可优化的问题。
- **配对/闭环设计**：如「创建联系人 + 回查是否恰好 1 条」，用两步互验把主观判断转成客观数量检查。
- 服务台助手的追问示例（密码重置 vs 账号解锁、VPN 申请 vs VPN 故障报修、软件安装权限 vs SaaS 账号开通等）是天然的「易混负样本」种子，可让 LLM 基于每一对批量生成混淆提问。

**③ 定期跑 + 追踪趋势**
- 用技术栈里摩擦力最小的方式跑（如 CI 每次变更触发）。
- **不能只看单次通过率，要看趋势曲线**——「这周比上周好了吗」。把测试结果连同 **prompt 版本**一起存档（存到 CI 之外便于长期分析），质量掉了能回溯是哪次改动导致。这就是「prompt 当代码管、版本化、可回归」的具体做法。

#### 5.1.4 通过率怎么定（PM 的产品决策）

- **视角转换**：通过率不是「我要多好」，而是「我能容忍多坏」——定的是可容忍的失败率。
- **按失败代价定，不按题目难度定**：先给测试按**严重度 S0–S2** 分级，再按级配通过率。
  - S0 硬伤（越权、编造、越界判断）→ **100% 零容忍，做成发布门禁**，不参与平均，一条 fail 即阻断上线。
  - S1 功能失败（路由错、推错资源）→ 高（如 95%+），核心区尤甚。
  - S2 体验缺陷（该追问没追问、啰嗦）→ 中（如 80–90%），可迭代。
  - 「优秀」为加分观察项，不进验收硬线（挪监控观察）。
- **冷启动无基线时**：先定「方向 + 相对关系」（谁必须比谁高），跑一轮拿真实基线，再把目标设成「基线之上的改进」，不空定长期达不到的理想值。
- **行动后果反检验**：每条线都要能回答「掉到线下我会做什么」（阻断发布 / 触发迭代 / 仅观察）；答不出行动的线是假指标。
- 通过率是给「一批题」的统计量，因此**场景集合的代表性**直接决定它是否有意义（连到 Day3 的真实分布采样）。

#### 5.1.5 组织落地：PM 在评测中的职责边界

Hamel 的方法预设「看数据 / 搭工具 / 提要求」是一个人的事；在 PM / QA / Dev 分工的组织里，需要把它翻译成协作。核心原则：**PM 定义「目标状态」，QA 定义「如何验证达到目标状态」。**

**职责分界尺：**

| 维度 | 谁定 |
|---|---|
| 测什么场景（覆盖哪些，尤其 S0、易混负样本、关键边界） | **PM** |
| 每个场景的期望行为（该做什么动作、达到什么结果） | **PM** |
| 多好才算过（通过标准、通过率、S0 零容忍） | **PM** |
| 关注哪些指标及其方向/优先级 | **PM** |
| 用什么题触发场景（具体出题、造多少、怎么造） | QA |
| 怎么判定一道题过没过（断言代码、评分表实现） | QA / Dev |
| 怎么跑、多久跑、用什么工具 | QA / Dev |

**PM 该产出的颗粒度**：到「场景类别 + 每类期望行为 + 通过标准（含 L1/L2 归属与通过率/零容忍）+ 关注指标及方向」为止。**规定「场景类别」而非穷举每道题**；具体出题、断言实现、评分表、跑测编排交给 QA。
> 这份测试目标文档的骨架 ≈ PRD 的状态流转表（产品里每个功能对应一行）＋ 能力边界分级 ＋ 通过率。给状态流转表每一行补两样：① 属 L1 还是 L2 ② 通过标准/通过率。

**指标该规定到哪（含两个坑）：**
- **分类型任务**（意图路由、资源匹配）→ 用**精度 + 召回**（分意图统计）；既怕漏又怕误时用 F1。PM 定「关注哪些 + 哪个优先」（如「误路由到端到端流程会误发起提交，精度优先」），**数值靠跑出基线后校准，不预先虚构**。
- **坑一：指标误用**——生成质量、追问质量、降级诚实度**没有唯一对错，不能套准确率/F1**，应走 L2 人工评通过率 / 人机一致率。在主观质量上硬套分类指标是错误。
- **坑二：类别不均衡**——真实流量里某意图可能占多数、badcase 极少，**别看单一总准确率**（全猜大类也能虚高），要**分意图 / 分场景类别统计**。

**看数据的分工**：PM 与 QA 看同一批数据，但目的不同——QA 为**执行**（过没过、覆盖够不够），PM 为**定义**（什么算好、哪些失败最该管、边界在哪）。PM 要争取的是**看原始 trace 的入口**（PM 本就该看用户数据，不越 QA 执行权），产出评分 rubric、S0 清单、badcase 分类与归因规范，供 QA 执行时使用。

**工具的处理**：看数据 / 打标工具不是 PM 亲手搭的杂活，而是 PM 写的**一份内部工具需求**（用户是评测团队）：把对话＋知识命中＋权限结果＋反馈聚合一屏、可按意图筛选、支持二元打标。冷启动期用**表格顶着**先跑通流程（Hamel 早期用 Excel 就跑通了 LLM 裁判对齐），再用证明的价值换正式排期——先轻量证明价值，再换资源。

#### 5.1.6 决策层心法：定严重度与通过率（PM 不可外包）

决策层的两件套：**严重度是因（按后果轻重给场景分级），通过率是果（按严重度给每级定达标线）**。两者背后是同一样东西——产品价值观：什么绝不能破（安全）、什么应该做到（准确）、什么最好做好（体验）。

**定严重度的心法：**

- **锚点**：严重度衡量的是「后果对用户/业务的伤害有多深、可不可逆」，**不是错误的大小，更不是团队修复的麻烦**。看似小的错（悄悄给了越权链接）可能 S0，看似大的错（答得啰嗦）可能 S2。
- **三把尺，任一指向严重就一票抬级（取最坏不取平均）**：
  1. **可逆性**：错了还能不能救回来？不可逆（已发起错误动作、已泄露、已给被当真的错误专业判断）→ 抬向 S0。触发了真实系统动作（发起工单、渲染可点链接）的错，可逆性变差，要上抬。
  2. **外部性**：伤害只停在对话里，还是溢出到真实世界（合规风险、让用户做错商业/法律动作、损害信任）？溢出 → S0。
  3. **违背哪种承诺**：安全 > 准确 > 体验。破坏边界/安全（越权、越界、编造）→ S0；破坏结果/准确（核心区该做对却错）→ S1；破坏处理/体验（降级不优雅、追问啰嗦）→ S2。
- **S0 要少而硬、能穷举**：S0 是发布门禁，权威来自稀少。能一条条列清的封闭清单（服务台助手约为：越权渲染链接、编造工程师/流程、越界替用户做高危审批判断、泄露他人账号信息……）。判据狠问题：「这条挂了还坚持上线，出事我能不能承担？」承担不起→S0。放太多红线，团队会绕过或偷偷降级，红线反而失效。
- **写判据而非只给标签**：不写「越权=S0」，写「越权=S0，因不可逆+有外部性+破坏安全承诺」。判据让定级稳定、可对齐（QA/技术/上级看逻辑而非看拍板）、边界变化时可复查。
- **拿不准先归中间级**：不确定是不是 S0 → 先放 S1 挂观察，别让红线注水；不确定能不能忽略 → 先放 S1/S2 记录，别直接判「不管」。上线后用真实后果校准（哪个 S2 引发大量投诉就升级）。

**定通过率的心法**（果，承接 5.1.4）：

- 视角：不是「我要多好」，是「我能容忍多坏」——定的是可容忍失败率。
- 按严重度配线：S0→100% 零容忍门禁（不参与平均，一条 fail 即阻断）；S1→高（如 95%+）；S2→中（80–90%）。
- 冷启动先定方向和相对关系（谁必须比谁高），跑出基线后再校准绝对值，不空定长期达不到的理想值。
- 行动后果反检验：每条线要能回答「掉到线下我会做什么」（阻断/迭代/观察）；答不出行动的线是假指标。


### 5.2 数据运营（上线后：数据驱动持续爬坡）

数据运营是一门关于**「数据流与归因」**的学问，核心不是"用什么评测手段"，而是：数据怎么来 → 怎么关联 → 怎么变成可归因的洞察 → 怎么驱动优化。方法内核：**亲自看大量真实数据、消除一切摩擦**（分数会骗人，原始对话不会）。

#### 5.2.1 运营总框架：五步闭环（起点前置）

```
[冷启动首轮] error analysis 发现真实高频失败 ──┐（起点：先看数据，不先定指标）
    ↓                                          │
① 监控什么指标（每个指标对应一类真实失败）      │
    ↓                                          │
② 数据怎么来（点踩 + 埋点 + 后台打标，三源）    │
    ↓                                          │
③ 怎么分析（按母表打标 → 数频次 → error analysis 找模式）
    ↓                                          │
④ 怎么优化（归因决定派谁修；高频边缘迁核心）    │
    ↓                                          │
⑤ 怎么确认优化了（对应指标降没降 + 看趋势）─────┘（循环）
```

**关键顺序修正：起点不是「定指标」，而是先做一轮 error analysis。** 若从"定指标"起步，容易滑向 Hamel 警告的无用通用指标（"连贯性 3.72→4.2 根本不知系统变好没"）。**指标必须从真实失败里长出来**：不是凭空决定"要监控追问率"，而是 error analysis 发现"该追问没追问"是高频失败，才去监控它。指标是失败的度量，失败要先被发现。

#### 5.2.2 先窄起步：定义 badcase 从哪开始（别煮沸海洋）

冷启动别想用母表一次覆盖所有失败。**先挑一个最高频、最可度量的失败，把它的完整闭环跑通**（来源：OpenAI/Sy Truong "avoid boiling the ocean"）。

- **第一轮的目的是验证「运营流程能不能转起来」，不是「抓得多」**。挑一个失败（如某类高频路由错、或"该追问没追问"），走通 发现→打标→归因→修→验证 全流程，再复制到别的类型。
- **要有明确的收尾指标**：能说清"这个失败降到多少算修好了"。

**第一轮抓 badcase 的优先级（按信号纯度）：**
1. **用户明确确认的失败（信号最纯，优先）**：对话里的更正（"不对，我要的是X"）、点踩（尤其带原因）、点"重新生成/编辑"——用户已替你判定这是问题，拿到即干净 badcase。
2. **系统客观标记的失败（无歧义）**：触发兜底（系统自认处理不了）、追问后用户流失、明确报错（链接失效）。
3. **行为推断的疑似失败（有噪声，谨慎）**：用户放弃、多轮未解决——进"疑似池"，靠抽样验证，不直接当 badcase 统计（见 5.2.6）。

#### 5.2.3 三个数据源：分工与关联

**三源分工（互补，覆盖不同盲区）：**

| 数据源 | 采什么 | 覆盖谁 |
|---|---|---|
| 点踩（用户主动反馈） | 用户明确的不满 + 原因选项 | 愿意开口的用户 |
| 埋点（用户行为） | 客观行为（点击、放弃、重新生成…） | 全量用户（含沉默的） |
| 后台打标（归因分类） | 给数据贴母表维度的标签 | —（是加工，非采集） |

> 系统主动信号（后台算，非用户动作触发）是运营主力，因为它覆盖沉默用户：兜底触发率、追问率、多轮未解决率、同问题复现率、行为/结果信号。

**三源关联：用 canonical feedback event 把三源钉在一起**（来源：OpenAI/Arize）。
- **不是三张表硬拼，而是设计一个统一的「反馈事件」结构**，把点踩、埋点、对话更正都汇进来；
- **关联键 = trace_id / conversation_id**：每个反馈事件都挂上对话标识符，于是点踩、埋点、打标天然指向同一段对话；
- **保留原始文本 + 出处（provenance），schema 支持「再处理」**：因为母表和打标器会演变，原始数据完整保留，母表升级后能拿旧数据用新分类重跑。**只存"打好的标"不够，必须存原始对话，否则母表一变历史数据就废。**

#### 5.2.4 点踩选项设计原则

点踩的精髓是**让用户点踩的动作，顺便完成 badcase 的初步分类**。

- **选项映射内部归因**：每个口语选项背后挂一个内部标签，映射到母表的失败类型/归因维度（如"没理解我的意思"→路由意图错；"回答不准确"→知识/生成）。使"用户点踩"直接成为"打标输入"。
- **让用户按「现象」选，而非「技术归因」选**：用户能准确感知"答错了/页面卡了"，但难准确区分"失忆 vs 一开始就没懂"（这是技术归因）。偏技术归因的选项（如"遗忘上下文"）收上来的标可信度低，后台要当"疑似"再核。
- **点踩与原因拆成两个独立事件、不选原因也算点踩**：先保召回（有没有不满意），再补精度（为什么）。懒得选原因的用户，纯点踩本身已是有效负向信号。
- **留"其他 + 自由输入"**：捞母表没预料的新失败类型（= 用户帮你做开放式编码），是发现母表盲区的入口。
- **万金油选项（如"没有帮助"）应去掉**：它无法反解到任何具体失败，制造脏数据；"不选也算点踩"已接住懒人，"其他"可做诚实兜底。
- **不做「点踩后追问」**：点踩时用户耐心已降，追问惹反感；大厂均不采用。

> 选项要贴合应用类型：服务台助手是"检索问答+轻操作型"，但若某类失败被架构根除（如资源与链接一一对应 → 不存在"资源匹配错"，给错必是上游内容判断错），则不必为它单列选项——好的架构能直接消灭一整类失败。

#### 5.2.5 后台打标方案

打标 = 给每条 badcase 贴母表维度的标签。**母表就是打标字典**（测试拿它当验收标准，运营拿它当打标字典，单一事实源）。

**三维打标：**

| 维度 | 取值 | 用途 |
|---|---|---|
| 失败层级（严重度） | S0 / S1 / S2 | 优先级、是否阻断 |
| 归因 | 路由意图 / 知识库 / 生成 / 系统前端 / 轻操作执行 | **决定派给谁修**（最关键） |
| 场景 | 母表编号（T01-1…） | 定位母表哪行、反哺 |

**打标的人机分工（同 error analysis）：** 人（PM/领域专家）先看数据、发现母表没有的新标签、定颗粒度（A）；LLM 按补全后的母表批量打标、计数（B）。

**打标器（分类器）必须版本化**（来源：OpenAI）：
- 当用 LLM 自动打标时，那个 LLM 就是"分类器"。
- **改了打标器的 prompt/逻辑，会让某类 badcase 统计假性波动**——你以为"产品变差了"（产品趋势），其实是"标尺变敏感了"（分类器更新伪装成趋势）。
- 故：母表和打标器每次变更都记版本；改了打标器要像校准 LLM-as-judge 一样重新校准，否则前后统计不可比。
- **按类别看精度，不看总精度**：不同类别误分类代价不同（呼应严重度），S0 类的打标精度要求远高于 S2。

#### 5.2.6 行为信号：推断而非确定，看趋势不看个案

行为信号（放弃、多轮未解决等）是**推断**出来的，单信号有噪声，需**证据序列组合**提纯：
- **"用户明确改正"**：结果卡 → 用户否定/重述同一意图 → 常伴随"重新生成"。序列组合置信度高。
- **"用户放弃"vs"闲聊结束"**：区分关键不是"有没有触发 ID"，而是"有没有『未被满足的明确业务意图』"——放弃=有业务意图但没点结果入口就中断；闲聊=从无明确业务意图。

**但即便组合也不完美**，故：**行为信号看群体趋势可靠，看个体判定不可靠**。正确用法——定一个"疑似"宽松规则（有业务意图+无结果入口点击+中断）捞进候选池，再**抽样估比例**，而非逐条精确判定。

> 采样偏差警告（来源：QASkills）：只看点踩样本会**高估失败率**（点踩是负向偏置样本，非随机）。算"整体失败率"不能直接用点踩池；报告要标明样本代表什么。

#### 5.2.7 信号价值分级：按信号价值分配处理成本

不同信号的信噪比不同，按价值分配处理成本（来源：IrisAgent + 真实项目实践）：
- **高价值信号（用户明确改正、带原因的点踩）→ 人工核**：信息量大、用户在意，值得高成本处理。
- **海量低信息信号（行为埋点、纯点踩）→ LLM 批处理 / 聚合统计**。
- 信号权重参考排序：明确改正 > 带原因点踩 > 纯点踩 > 会话放弃。

#### 5.2.8 error analysis：运营的分析引擎

（badcase 打标与母表校准的方法，运营循环第③步"怎么分析"的核心。源自 Hamel/Shreya：open coding → axial coding → 理论饱和。）

**四步流程：**
1. **建数据集**：收集有代表性的交互 trace（trace = 输入 + 系统输出）。
2. **开放式编码（人做，PM/领域专家主导）**：先不看母表，像"记日记"忠实记录每条 trace 的**第一个失败**（上游错引发下游连环错，第一个失败通常是根因）。
3. **轴向编码**：把零散笔记归纳成失败分类法，并**数每类频次**（把"一团定性问题"变成"按频次排序的作战地图"）。
4. **迭代到理论饱和**：新 trace 不再冒新类别即停。口诀：先看满 100 条打底，之后连续约 20 条无新类别即停。**抓真实高频失败，不求穷尽**。

**三个关键洞察：**
- **① 起点破环**：error analysis 要看交互，但它又是第一步——冷启动没数据？破解：交互=输入+输出，缺的只是输入，输入可**合成**；合成的先验来自**演绎资产**（PRD 业务定义 + PRD 真实语料 + 母表假说）。但合成只覆盖"想得到的"，**上线/灰度真实 trace 不可替代**（带来想象力之外的失败）。
- **② 人机分工**：轴向编码含两子任务——**A 发现类别**（创造性、需突破现成分类）**必须人做**（自下而上归纳、先不看母表、再比对母表查缺补漏、由人定颗粒度）；**B 套用类别+计数**（机械、需规模一致）**交 LLM**（此时用补全后母表当依据天经地义）。"用 LLM 帮忙"指的是 B 不是 A；拆开后"发现盲区"与"用母表当依据"不再冲突。
- **③ 演绎 × 归纳互补**：母表是**演绎假说**（从方法论+PRD 推出），error analysis 用真实数据**归纳校准**。最优路径 = 演绎打底（母表给方向）+ 归纳校准（数据补全意外），循环迭代。

**嵌入两轮测试的完整流程：**
```
[冷启动·第一轮：探索，产出校准后的母表]
1 建数据集：PRD 语料 + 母表指导 → 合成刁钻输入 → 喂系统 → 合成 trace
2 开放式编码（人）：先不看母表，记录每条 trace 第一个失败
3 轴向编码：A 发现类别（人：归纳→比对母表查缺补漏）B 套用+计数（LLM）
4 迭代到饱和：满 100 条打底，连续 20 条无新类别即停；抓高频
   → 产出：母表 v+1（数据校准）+ 每类频次/优先级 + 稳定分类标准
[第二轮：正式测试，用校准后母表测达标]
[上线后：点踩 trace 优先采样 → 持续 error analysis → 母表持续进化]
```
> 第一轮（探索）≠ 第二轮（验收）：第一轮产出的是"更好的母表"而非"通过率"，允许乱、允许覆盖不全；勿用验收标准苛求第一轮。

#### 5.2.9 归因与派单

- **归因靠基础设施，不靠拍脑袋**：归因（路由/知识/生成/系统/执行）是靠 **可搜索的 trace + 能自动标错的断言** 查出来的：走错门→查 router；答不全→查知识库/生成；人设崩→查 system prompt。
- **归因决定派单**：归因维度是运营与研发的接口——归因打对，badcase 才自动流到对的人。
- **高频边缘 → 迁核心**：运营最有产品价值的产出——发现某个高频边缘场景值得投入，把它从边缘能力升级为核心能力。
- 归因只在实际表现不达标后进行，**不把未经验证的推测写回能力边界**。

#### 5.2.10 隐私与数据治理（服务台助手尤其）

反馈系统一开始就要定清隐私规则（来源：OpenAI）：谁能看原始对话、数据留存多久、哪些要脱敏、哪些下游 agent 可检索原始对话。服务台助手涉IT 服务数据（含员工账号、设备信息），此项不可省。**聚合信号只有在采集政策对负责人清晰可读时才有用。**

### 5.3 生成把关（上线前后都用：把能力边界写进 prompt 并守住）

生成把关 = PM 对"技术写的提示词够不够、守没守住能力边界"的把关。方法来源：Anthropic Prompt Engineering 官方文档 + 真实项目实践。

#### 5.3.1 前提：prompt 工程之前先有"框架标准"

动手调 prompt 前，需要三件套：**成功定义 + 测试方法 + 初稿**，否则是盲目优化。
- **"成功标准"有两层**：框架标准（能力边界、各区期望、边缘处理）> 测试题（用例）。**框架是母、测试题是子，框架先行**。
- 框架标准（= 能力边界母表）的双重用途：① 指导 prompt 该写什么 ② 做把关 prompt 的标尺（prompt 有没有覆盖框架里每个边界和边缘处理）。**没有母表，prompt 把关无从谈起；有了它，把关就有了标尺。**
- 核心心法：**把写 prompt 当成给"绝顶聪明但对你项目零背景的新员工"下指令**——它不缺智力，缺你脑子里的业务背景和隐含预期，"你觉得不用说的"恰恰最要说。

#### 5.3.2 prompt 不是万能药：先归因，且要归到"哪一段 prompt"

- 不是每个失败都该用 prompt 解决。把关前先归因：是 prompt 问题，还是知识供给/系统问题？知识库缺内容用 prompt 打补丁是南辕北辙。
- **归因维度不是"prompt vs 非prompt"，而是"哪个环节 / 哪一段 prompt"**：一个 agent 有多段 prompt——路由/意图识别（是一段 prompt）、匹配/检索、回复生成（另一段 prompt）——加上非 prompt 的知识供给、系统工程。
- 关键澄清：**"改 router"和"改生成 prompt"都是改 prompt，但是不同段**。归因要精确到"该改哪一段"：意图判错→改路由那段 prompt；话术不对→改生成那段 prompt；内容缺失→改知识库（prompt 救不了）；接口错→改系统。**精确到"哪一段"，技术才不会改错地方**（看 trace：意图那步就错→改路由；意图对后面错→往下游找）。

#### 5.3.3 提示词技术阶梯（从最有效到最精细）

Anthropic 的技术是有顺序的阶梯，不是零散技巧：

1. **清晰直接的指令**（最有效）：正向说"要什么"（不只说"不要什么"）、给顺序步骤、具体到可执行。判据：零背景新员工照做能不能不用猜。
2. **多示例**：给"输入→理想输出"，尤其放**边界/易混场景**的正负例（母表里的易混场景既是测试题也是最该放的示例）。判据：prompt 有没有放示例、有没有覆盖易混场景。
3. **思维链（CoT）**：让模型先写推理再给结论，强迫它真正走一遍中间步骤，提升复杂任务准确性。但增延迟成本，只用在值得多想的任务；**新推理模型已内化 CoT，不必手动加**。（与服务台助手"推理式澄清"同源——都是"让模型把内部推理外显"，一个给自己看提准确、一个给用户看消歧义。）
4. **XML 标签**：给 prompt 搭结构，让模型分清指令/背景/示例/用户输入；关键规则要被明确框出而非埋在段落里；长文档放前、query 放后（可提升约 30%）；标签语义化且前后一致。
5. **角色设定**：一句话调动一整套隐含行为的强力杠杆（"你是资深 IT 支持工程师"隐含专业、严谨、谨慎）。但**只定大方向、定不了细节**——人设不能只写"你是谁"。

#### 5.3.4 system prompt 该放什么 + 8 条把关清单

system prompt 放"全局稳定的身份和行为准则"。一个完整人设含五层：① 角色/身份 ② 能力声明（尤其"明确不做什么"）③ 行为规则（追问/兜底/语气）④ 红线（S0，显式）⑤ XML 结构化承载。

**8 条把关清单（技术给你一版 prompt，逐条核）：**
1. 角色：定了吗？调子对不对？
2. 能力声明：写了"能做什么"吗？尤其"明确不做什么"？
3. 追问逻辑：什么情况追问、追问什么，写清了吗？（不是笼统"信息不全就问"）
4. 兜底逻辑：什么情况兜底、传达什么、后续动作，分类写清了吗？
5. 红线（S0）：绝不能做的，显式列出、在 system 层吗？
6. 具体可执行：每条规则，零背景新员工照做能不用猜吗？
7. 结构化：分块了吗（XML），还是糊成一坨？
8. 抗漂移：最关键的规则，放在显著位置、够突出吗？（长对话会稀释 system 规则，关键规则要钉在显著位置、结构化，别指望模型自己一直记住）

#### 5.3.5 system prompt 的详略分寸（写准，不是写全）

把关最难的手感——不是"越详细越好"，而是"该细的细、该留白的留白"。三把尺决定"什么进 system prompt"：

- **影响行为吗？** 影响行为的背景才放（服务对象、身份定位、使用场景），纯介绍性的不放（公司简介、无关品牌史）。例：服务台助手"服务内部员工非外部客户"要放（影响语气边界），"某企业成立于X年"不放。
- **能不能变？** 不能变的（红线、判断规则、核心信息）→ 写死、写具体；可以变的（措辞、语气细节）→ 给"要点 + 示例"，别逐字锁死。
- **能直接执行吗？** 能→够了；要猜→写具体到能执行。

**兜底怎么写（示范这个分寸）：判断规则必须写死**（何时走哪种兜底 + 判断标准），**但话术不必逐字锁**——用"要传达什么（要点）+ 示例语气"承载。判断和核心信息不漂移，措辞留自然度（否则回复僵硬像机器人）。

> 警惕反面：system prompt 不是越全越好。太长→关键规则被淹没；规则太多→互相冲突；话术锁太死→僵硬。目标是"写准"不是"写全"。

#### 5.3.6 Skill：场景化按需加载的 prompt（prompt 体系分层）

5.3.1–5.3.5 讲了 system prompt 该写什么、怎么把关、怎么拿捏详略。但有一个结构性问题始终没解：**system prompt 承载的东西越多，5.3.5 警告的三个反面就越难避免**（太长→关键规则被淹没；规则太多→互相冲突；话术锁太死→僵硬）。根源在于 system prompt 是**全局常驻**的——每轮对话都完整加载，不管用户当前在什么场景。当产品有多个场景、每个场景有自己的操作规程时，全部塞进 system prompt 就会互相稀释。

Skill 是这个问题的解法：**把 prompt 体系从"一整坨 system prompt"升级为"system prompt（全局层）+ skill（场景层）"的两层结构。**

##### 5.3.6.1 Skill 的定义

Skill = **场景化按需加载的 prompt**。它本质上就是一份 prompt，但有两个关键区别：

- **按需加载**：平时只占一行触发描述（几十 token），命中场景后才把完整指令加载进上下文。不命中时不消耗 token、不稀释全局规则。
- **场景化**：每个 skill 服务于一个具体场景（如"兜底处理""查流程""找模板"），内部可以规定该场景的完整操作规程——步骤、顺序、该调什么工具、输出格式、语气要求、边界处理。

一句话：**system prompt 是"你是谁、全局怎么做"，skill 是"遇到这个场景、具体怎么做"。**

##### 5.3.6.2 Skill 与 MCP、Plugin 的区别

三者解决的问题完全不同，不可混用：

| | 解决什么问题 | 本质 | 例（服务台助手） |
|---|---|---|---|
| **Skill** | 模型有能力做，但不知道**按你的标准怎么做** | 场景化的操作规程（prompt） | "兜底回复的操作规程"——先说什么、后说什么、哪些信息必须包含、语气要求 |
| **MCP** | 模型**碰不到外部系统和数据** | 外部连接通道（工具调用协议） | 查 ITSM 获取流程入口、调用 工程师数据接口 |
| **Plugin** | 需要把 skill + MCP + 命令**打包分发**成一个可安装单元 | 分发和组合的壳 | 把服务台助手的全套能力（知识检索 skill + ITSM 连接 MCP + 兜底 skill）打包给其他团队复用 |

**关系**：Skill 里可以规定"第几步用什么 MCP 工具"；Plugin 里可以包含多个 skill 和多个 MCP。三者是嵌套关系，不是互斥关系。

**判断口诀**：
- 失败是因为"连不上外部系统" → MCP
- 失败是因为"模型知道该做什么，但不知道按你的方式怎么做" → Skill
- 需要把一整套能力打包给别人用 → Plugin

##### 5.3.6.3 什么时候该用 Skill（适用条件）

**归因检查清单（逐条排除后，剩下的就是 skill 的活）：**

| 排除项 | 如果是，该改什么 |
|---|---|
| 模型连不上外部系统/数据 | → MCP（加接口） |
| 流程走向需要编排（多步调工具、看结果再决定下一步） | → Workflow（代码编排） |
| 需要模型自主规划未知流程 | → Agent |
| 模型推理能力不够（复杂逻辑、多步推导） | → CoT / 推理模型 |
| System prompt 里的全局规则本身写错或缺失 | → 改 system prompt |
| 知识库/数据缺内容 | → 补知识库 |

**以上都不是，但模型的执行质量仍然不稳定——它知道该做什么，但不知道按你的标准怎么做**：→ 这就是 skill 该做的事。

**典型信号**（出现以下情况，大概率需要 skill）：

1. **同一场景，每次执行的方式不一致**——格式、步骤顺序、信息组织、详略程度每次不同，但 system prompt 已经写了规则。说明规则太抽象，该场景需要一份具体操作规程。
2. **某个场景的操作规程足够复杂，塞进 system prompt 会淹没其他规则**——比如兜底处理有五种子情况各自的话术要点和后续动作，全放 system prompt 会把路由规则挤到角落。
3. **不同场景之间的规则互相干扰**——"查流程"要求严谨克制、"闲聊兜底"要求温和引导，两套语气规则放在同一个 system prompt 里模型会混用。
4. **System prompt 改一处、别的场景表现漂移**——因为全局规则太多，改动一条的涟漪效应波及其他场景。

##### 5.3.6.4 System prompt vs Skill 的分工原则

**什么留在 system prompt（全局层）：**
- 角色身份（"你是服务台助手，某企业内部的 IT 服务台 AI 助手"）
- 能力声明（能做什么、明确不做什么）
- 全局判断规则（什么情况追问、什么情况兜底、什么情况拒答——**判断条件**，不是执行细节）
- S0 红线（绝不能做的，显式列出）
- 全局语气基调
- **Skill 索引**（告诉模型"有哪些 skill、每个什么时候触发"——不需要 skill 的完整内容，只需触发描述）

**什么抽成 skill（场景层）：**
- 某个场景的完整操作规程（步骤、顺序、每步该做什么）
- 该场景下调什么工具、按什么顺序调
- 该场景的输出格式和信息组织要求
- 该场景的语气和话术要点（不是逐字锁死，而是"必须传达什么 + 示例"）
- 该场景下的边缘处理和降级方式

**分工的判断口诀**：system prompt 管"什么时候走这条路"（判断规则），skill 管"走上这条路后怎么走"（执行规程）。

**以服务台助手兜底为例——两层分离：**

```
[system prompt 里只写判断规则]
当以下任一条件成立时，进入兜底处理：
- 用户需求超出产品能力范围（界外区）
- 知识库无法支撑完整回答且追问无法解除限制（边缘区降级）
- 系统返回异常无法正常完成
→ 具体兜底操作参照 skill:fallback-handling

[skill:fallback-handling 里写执行规程]
兜底处理操作规程：
1. 先确认：用什么证据判定进入兜底（知识库无命中 / 系统异常 / 界外判定）
2. 回复结构：
   - 第一段：说明能做到的部分（如有），不以道歉开头
   - 第二段：诚实说明当前做不到什么、为什么
   - 第三段：给出真实可用的下一步（人工渠道/替代路径），不编造
3. 分情况处理：
   - 界外需求 → 明确说明不在服务范围 + 给真实移交路径
   - 知识不足 → 说明已确认部分 + 标注不确定部分 + 建议联系IT 支持团队
   - 系统异常 → 说明当前服务临时受限 + 给替代联系方式
4. 禁止：编造能力/原因/移交结果；把不确定说成确定
5. 语气要点：克制、不过度道歉、不甩锅（示例："目前我能确认的是……但关于……建议直接联系IT 支持团队，他们能给你更准确的判断。"）
```

##### 5.3.6.5 Skill 内部该写什么（结构）

一个 skill 的完整结构：

1. **触发描述**（一句话，平时常驻于 system prompt 的 skill 索引中）：什么场景命中这个 skill。
2. **前置条件**（可选）：进入此 skill 前应已确认什么（如"已判定用户需求属于界外区"）。
3. **操作步骤**：按顺序规定该场景下的完整执行流程——每一步做什么、调什么工具（如有）、输出什么。
4. **输出规范**：该场景的回复结构、信息组织、格式要求。
5. **分支处理**：该场景内部的不同子情况及各自的处理方式。
6. **边界与禁止**：该场景下特别要避免的错误（可呼应母表中该场景的 S0/S1 要点）。
7. **语气与话术要点**：不逐字锁死，给"必须传达什么 + 示例语气"（同 5.3.5 的分寸原则）。

**设计原则：**

- **一个 skill 对应一个场景，不塞多个**——"查流程"和"找模板"是两个 skill，不是一个"查东西"skill。颗粒度对齐能力边界母表中的场景分类。
- **Skill 内部的详略同样遵循 5.3.5 的三把尺**——判断规则写死、话术给要点、能执行即可。Skill 不是第二个 system prompt，不能又变成一大坨。
- **Skill 可以规定工具调用顺序**——"第一步查知识库、第二步查 ITSM 获取入口、第三步组装回复"，这让 skill 成为 workflow 节点内部的操作手册（skill 不决定流程走向——那是 workflow 的事——但决定某一步内部怎么执行）。
- **Skill 与母表的关系**：母表定义"该场景期望什么结果"（验收标准），skill 规定"该场景怎么执行才能达到那个结果"（操作手册）。母表是"要什么"，skill 是"怎么做"。
- **Skill 的测试**：skill 不改变测试方法——仍然用母表的期望行为和 L1/L2 判定。Skill 改变的是"为了达到期望行为，模型拿到的指令是什么"。如果加了 skill 后该场景的通过率提升，说明之前的失败确实是"不知道怎么做"而非"做不到"。

##### 5.3.6.6 与方法论其他部分的关系

- **与 5.3.2（prompt 不是万能药）相通**：归因到"哪一段 prompt"时，skill 是一段独立的 prompt。归因发现"查流程的回复格式不稳定"→ 改的是 skill:query-process，不是 system prompt，也不是 workflow。
- **与 5.3.5（详略分寸）相通**：skill 是 system prompt 膨胀问题的结构性解法——不是把细节砍掉，而是把细节放对地方。全局层精简（写准），场景层丰富（按需加载）。
- **与 5.4（架构选择）相通**：skill 不改变架构。Workflow 决定流程走向，skill 决定某一步内部的执行质量。一个 workflow 节点的内部可以加载一个 skill 来提升该步的稳定性（见 5.4 第零刀）。
- **与能力三区相通**：核心区的 skill 应覆盖完整操作规程（保证结果）；边缘区的 skill 应包含降级处理（保证处理）；界外区的 skill 应规定边界表达和移交路径（保证边界）。

### 5.4 架构选择：CoT / workflow / agent / skill 与自主性

一个多步 AI 任务，先问"步骤谁定的、决定权归谁"，据此选架构。这决定了能力边界如何在系统层落地。**但在动架构之前，先排除一个更轻量的可能。**

#### 5.4.1 第零刀：是不是根本不需要改架构？

改架构前先问：**失败是出在"流程走向"，还是出在"某一步的执行质量"？**

- **流程走向错**（该走 A 路走了 B 路、该调工具没调、该追问直接硬答）→ 这是架构问题，往下看第一刀、第二刀。
- **流程走向对，但某一步执行得不好**（走到了正确的兜底分支，但兜底回复的格式/信息组织/语气每次不一样；走到了正确的查流程节点，但回复的信息结构不稳定）→ **这不是架构问题，是 skill 问题。**

Skill 是最轻量的干预手段：不改 workflow 编排，不改 system prompt 全局规则，不引入 agent 自主性——只在那一步给模型一份具体的操作规程，告诉它"这个场景下按这个方式做"。按需加载，只在该步生效，不影响其他场景。

**判断口诀**：如果把问题描述成"模型知道该做什么，但不知道按我的标准怎么做"，那就是 skill；如果描述成"模型走错了路"或"模型没有走该走的路"，那才需要改架构。

> 与归因相通：5.3.2 说"归因要精确到哪一段 prompt"——skill 正是让归因可以精确到「某个场景的操作规程」。改了 skill:fallback-handling，只影响兜底场景；改了 system prompt 的路由规则，可能影响所有场景。**能用 skill 解决的，不动 system prompt；能用 system prompt 解决的，不动架构。** 干预手段的优先级：skill（场景级）→ system prompt（全局级）→ workflow/agent（架构级），从最轻到最重。

#### 5.4.2 第一刀：步骤由谁决定

| 步骤来源 | 用什么 |
|---|---|
| 模型临场想（我不知道步骤） | 纯思考 → CoT / 推理模型；要调工具自主规划 → agent（含 planning） |
| 人已知步骤（我知道正确流程） | 纯思考顺序不调工具 → 写进 prompt（规定好的 CoT 模板）；要调工具有分叉 → **workflow 编排** |

- **CoT 是给"模型临场想"用的，不是给"人已知步骤要它照做"用的**。当人已有明确步骤（尤其涉及调工具、看结果、再行动），正确实现是 **workflow（代码编排），不是 CoT，也不是让 agent 自主 planning**——已知的流程该固定，别让模型每次重想（引入不稳定）。呼应《Building effective agents》："能用 workflow 就别用 agent"。

#### 5.4.3 第二刀：workflow vs agent 的真正分界 = 谁决定"下一步走哪"

- **分界不在"用不用 AI 思考"，而在"谁决定下一步走哪"**：
  - **workflow**：流程走向由代码/预定义规则决定。AI 可在**某一步内部**做任意复杂思考（含理解自然语言、语义判断），但"下一步走哪"由代码根据 AI 这步的输出决定。
  - **agent**：流程走向由 AI 自己决定（自己决定调什么工具、要不要继续、如何 planning）。
- **判断口诀**：把那一步的 AI 换成"一个输入模糊、输出确定的超级聪明函数"，若整个流程还能按你画的流程图跑 → **workflow**；若流程图本身要靠 AI 临场决定 → **agent**。
- **推论**：工具返回自然语言、需 AI 理解语义 → 仍是 workflow（在 workflow 里套一个"AI 解读成结构化结果"的步骤完全正当，AI 是那个"输入模糊输出确定"的智能节点，不是流程决策者）。
- **AI 解读步骤应输出置信度**：低置信度走"追问/兜底"分支（= 边缘区的技术实现），仍是 workflow。

#### 5.4.4 企业场景：自主性能少则少

企业 AI 产品的自主性是一条光谱（纯 workflow ←→ 纯 agent），**企业场景大多偏左**（以确定流程为主、少数节点嵌 AI 判断）。原因：

1. **错误代价高、要可控可审计**：企业场景错误常不可逆（报错款、给错法律指引），而 agent 的自主性 = 不可预测性；企业要能解释"每步为什么这么走"，workflow 可审计、agent 难审计。
2. **正确流程通常已知**：企业本有确定业务流程/制度，既然已知就该 workflow 固定，让 agent 探索已知答案是自找不稳定。
3. **要稳定一致**：agent 每次"想"的可能不同，同一输入不同次走不同路；企业要一致性。

**原则**：自主性能少则少——只给到"确实需要智能判断且无法预先确定"的节点，其余用 workflow 固定。更成熟的企业 AI 设计是"把 AI 关进 workflow 的笼子、只在该放权处放一点权"。

> 与能力边界相通：**核心区（确定能力）适合 workflow 固定，边缘区（需判断）才需要模型推理**。
> 服务台助手/报销助手大概率是"workflow 为骨架 + 少数节点嵌 AI"的混合体，不是纯 agent。服务台助手的"推理式澄清"更是把 AI 自主判断转化为用户选择，又收回一层可控性——这在企业场景恰是更安全的设计。

#### 5.4.5 自主性定级工具：错误代价 × 可检测性矩阵

5.4.4 说"自主性能少则少"，但具体哪些动作可以放、哪些必须收？不是笼统给"整个产品"定一个安全级别，而是**给每个动作**按"错误代价 × 可检测性"分别判断。

```
                     错误易发现              错误难发现（静默损坏）
高错误代价    带人工审批部署            别部署，除非有严格护栏
低错误代价    可放心自主部署            带监控部署
```

**使用方式：把产品的每个动作/功能分别放进矩阵的格子里。**

以报销助手为例：
- "查询报销进度"：低代价 + 易发现 → 左下角，可自主
- "提交报销"：高代价（报错款不可逆）+ 可能难发现（悄悄提交了错的）→ 右上角，必须有严格护栏（执行前确认 + 人工审批）

以服务台助手为例：
- "查流程入口"：中等代价（给错了用户还会自己判断）+ 相对易发现 → 可带监控部署
- "越权展示不该看的内容"：高代价 + 难发现（用户不知道自己不该看到这个）→ 必须有严格护栏

**关键认知：同一个产品的不同功能，落在不同格子，该给的自主权和护栏也不同。** 这张矩阵把 5.4.4 "企业要收自主性"的直觉，变成了一把可操作的尺——不是笼统保守，而是按动作精确定级。

> 与方法论的映射：矩阵的"高代价"格子 ≈ S0 红线（零容忍、不可逆）；"可检测性"对应 5.2 数据运营里的行为信号设计（能不能在生产中自动发现这类错误）。

#### 5.4.6 能力不足时：缩范围，不加编排

当某个环节 AI 做不可靠时，直觉反应是"再包一层 agent 让它更聪明"或"加一个 orchestration 层编排它"。**这个直觉是错的。** 正确做法（按优先级）：

1. **缩小范围（narrow scope）**：让这个环节只处理它能可靠处理的子集，其余走降级/人工。
2. **简化问题**：去掉依赖弱能力的步骤，用更简单的方式达到同样目的。
3. **加脚手架（scaffolding）**：用确定性的工具补偿——比如加一个校验器提前拦错，而不是加一个"更聪明的 AI"来审查第一个 AI。

**本质**：不可靠的环节需要的是"减少它需要做的事"或"用确定性工具兜底"，而不是"让它做更多的事"。这与 5.4.4 "能用 workflow 就别用 agent"一脉相承——遇到问题时往确定性方向走，不往自主性方向走。

> 呼应能力三区：当某功能实测表现不稳定，第一选择不是升级架构让它变稳定，而是考虑把它从核心区降到边缘区（承认能力边界、设计降级路径）。架构升级是手段，不是目标——能用边界设计解决的问题，不用架构解决。

### 5.5 生产护栏与可靠性（上线后的系统级保障）

5.1–5.4 分别讲了测试（上线前门禁）、数据运营（上线后爬坡）、生成把关（prompt 层）、架构选择（编排层）。但还缺一块：**上线后在生产环境里实时运行的系统级保护机制**——护栏（guardrails）、可靠性机制、human-in-the-loop。

这不是测试（测试是上线前的），也不是数据运营（数据运营是事后分析改进的）。这是**实时运行时的保护层**——模型每一次输出都经过的检查和拦截。

#### 5.5.1 三层护栏：按"在哪拦"分

护栏不是一个笼统的概念。按"拦在流水线的哪个位置"分三种，每种解决不同的问题，不可互相替代：

```
用户输入 → ①输入护栏 → 核心处理（路由/匹配/生成）→ ②输出护栏 → ③流程护栏 → 返回用户/执行动作
```

**① 输入护栏——拦在"模型还没处理之前"**

在用户输入到达核心逻辑之前先过筛：有没有注入攻击（prompt injection）、有没有越权请求、有没有不该处理的内容。

**关键设计原则：输入护栏应该是一个独立的处理步骤，不是混在回答 prompt 里的一句话。** 让同一个模型同时"回答好"和"筛查严"，两个目标会互相干扰——为了回答好可能降低筛查敏感度，或为了筛查严而过度保守。用一个独立的模型实例（或规则引擎）专门做筛查，与核心回答模型分开，各管各的，互不妥协。

这和 workflow 思路一致——**护栏是 workflow 里的一个独立节点，不是混在回答 prompt 里的一句话**。

> 与方法论映射：输入护栏的职责 ≈ 界外区识别（超范围/禁止项拦截），但它不是 prompt 里的一条规则，而是一个独立的系统步骤。

**② 输出护栏——拦在"模型输出之后、返回用户之前"**

模型给了回答，在返回给用户之前再过一道检查：有没有泄露不该说的（内部 UUID、敏感数据）、格式对不对、有没有越界判断。

**关键洞察：5.1 里讲的 S0 断言（"输出不含 UUID""无权限时不含链接"），不只是测试时跑的——它们可以在生产环境实时跑。** 每次模型输出都过一遍 S0 断言，不等测试才发现，而是上线后每一次都拦。这是断言从"测试工具"到"生产护栏"的升级——同一套规则，两个用途。

> 与方法论映射：输出护栏 = S0 红线断言的生产环境实时化。5.1.3 里定义的 S0 通用断言（不绑定 feature、全局必须成立），直接变成生产环境的实时检查器。

**③ 流程护栏——拦在"关键动作执行之前"**

在真正触发不可逆操作（提交报销、发起审批、发送通知）之前，强制停下来确认。这是最后一道闸。

> 与方法论映射：流程护栏 = 4.3 任务型应用变体里写的"不可逆或高风险动作应更保守，并在执行前确认"的系统级实现。

**三者各防不同问题：**
- 输入护栏防"不该进来的进来了"
- 输出护栏防"不该出去的出去了"
- 流程护栏防"不该做的做了"

#### 5.5.2 三个可靠性机制（agent 自救的三件套）

护栏是"外部拦截"，以下三个机制是"agent 自身的可靠性能力"——让 agent 自己知道做没做对、能不能自我纠正。

**① 每步从环境获取 ground truth（真实反馈）**

Agent 执行每一步后，都要从环境拿到"真实结果"来判断进度——工具调用返回了什么、系统状态变了没有、操作成功了没有。而不是让 AI 凭想象继续。

- 报销助手提交报销后，必须拿到系统的真实回执（成功/失败/错误码），而不是 AI 假设"应该成功了"
- 服务台助手查询 ITSM 后，必须拿到真实返回的流程 ID，而不是 AI 凭记忆猜一个
- **判断一个环节能不能自主的前置条件：它能不能拿到真实反馈。** 能拿到 → 可以更自主（因为能自我验证）；拿不到 → 必须加外部检查或人工兜底

> 这就是为什么"编码"是理想的 agent 场景——代码能跑测试、看报错、自我纠正。而"法律建议"不是——给完建议后没有即时反馈告诉 AI 建议对不对。

**② 验证循环（verification loop）**

在 agent 的流程中内嵌"检查自己的工作"的环节。核心判断：**评估任何环节能不能自主，先问"它能不能验证自己做对了"。能验证 → 可以更自主；不能验证 → 需要人或工具兜底。**

- 服务台助手匹配了一个流程后，能不能自己检查"这个流程是否真的对应用户问的场景"？如果能（比如拿流程标签和用户关键词做一次核验），这步可以更自主
- 报销助手填完了报销表单，能不能自己检查"金额和发票是否一致"？如果能（调一个校验工具），这步可以更自主

**设计 verification loop 的优先级**：
1. 最好：用确定性工具验证（代码断言、规则引擎、数据比对）——结果确定
2. 其次：用独立模型实例验证（一个模型生成，另一个模型检查）——比自己检查自己更可靠
3. 最差：让同一个模型自己检查自己——容易自证正确（"我说得对因为我就是这么想的"）

> 与 5.4.5 矩阵对应："可检测性"维度的本质就是"有没有 verification loop"。有 → 错误易发现 → 可给更多自主权；没有 → 错误难发现 → 需要更强护栏。

**③ 错误恢复（error recovery）**

可靠的 agent 需要清晰的停止条件和错误恢复策略。失败了怎么办要预先设计——不能等失败了再临场想。

这正是方法论 4.3 已经写的："停止与恢复：失败、超时、重复、撤销和人工接管需要明确路径。" 补充具体路径：

- **重试**：对瞬时故障（网络超时、API 限流），可自动重试，但需有重试上限
- **换路径**：对能力边界内但当前路径失败的（检索未命中），尝试替代方案（换检索策略、扩大匹配范围）
- **降级**：对边缘区问题，走安全降级（不硬答，给出"目前能确认的部分 + 移交建议"）
- **转人工**：对超出恢复能力的，清晰移交（带上已获取的上下文，不让人从头开始）
- **停止**：对检测到可能造成不可逆损害的，立即停止（不重试、不换路径，直接兜底）

#### 5.5.3 Human-in-the-loop：不是"要不要"，而是"在哪个点、以什么方式"

**自主权是"挣"出来的，不是一步到位给的。** 实操路径分三个阶段：

**阶段一：灰度/早期——全量人审 + 强护栏**
- 三层护栏全开（输入/输出/流程）
- 高风险动作全量人审（每条看）
- 目的：发现问题、建立信任、积累"哪些动作稳、哪些不稳"的数据
- 5.4.5 矩阵的所有格子都默认从最保守开始

**阶段二：放量——选择性人审 + 聚焦护栏**
- 稳定的动作放开自主（矩阵里低代价+易发现的格子）
- 不稳定的保持人审（矩阵里高代价+难发现的格子）
- 护栏聚焦：输入护栏可能放松、输出和流程护栏保持
- error analysis 持续（5.2），发现新问题类型 → 加新护栏

**阶段三：成熟——agent 主动上报 + 监控为主**
- **教 agent 识别"我拿不准"，主动上报人审**——而不是靠人去逐条检查。这比"人主动检查"更好：人检查容易漏、成本高；agent 主动上报让人只处理真正需要判断的。这正是方法论里"边缘区追问/降级"的另一种形式——agent 自己说"我拿不准，让人来"
- 人审只处理上报的 + 抽样复检
- 护栏内化到系统，运营靠监控指标
- **但矩阵右上角（高代价+难发现）可能永远保持护栏，不降级**——对应 S0 红线的系统级体现

**Human-in-the-loop 的隐性风险：自动化偏差（automation bias）**

当模型大部分时候做得对，人类审核员会变麻木，开始无脑信任模型而忽略细节。攻击者或系统性错误会利用这一点——把有问题的动作埋在大量正确动作里，让疲劳的人审漏过。

应对：
- **人审要有针对性**——不是"每条都审"，而是"只把高风险/低置信的送去审"（呼应 5.2.7 信号价值分级：把最贵的人工判断成本花在信号价值最高的样本上）
- **审核界面要把"需要人判断的点"高亮出来**，别让人在一堆正确信息里找那一个有问题的
- **定期刷新审核策略**，防止人审变成"机械点通过"

> 三阶段路径的本质：**自主权按已证明的可靠性逐步放开**——先全量审→放手稳的→保持审不稳的。有些格子可能永远不放（高代价+难发现）。这不是"偷懒少审"，而是"把有限的人力集中在真正需要人判断的地方"。

## 六、AI 产品观（贯穿全篇的底层认知）

方法论的所有细节，最终收敛到几条产品观——它们是做 AI 产品时反复回到的判断原点。

**① AI 产品的本质是一连串 tradeoff，取舍的主体是 PM。**
几乎没有"对/错"的决策，全是取舍：通过率高低（召回 vs 精度）、workflow vs agent（可控 vs 灵活）、system prompt 详略（明确 vs 臃肿、不漂移 vs 不僵硬）、点踩选项（用户成本 vs 数据质量）、严重度（保守拦截 vs 放行体验）、合成 vs 真实数据（快启动 vs 覆盖真实）。传统软件很多东西是确定的，AI 产品处处是概率、边界、自由度的权衡。**工程能实现，但"往哪边取舍"是产品判断——PM 的核心价值不是"写清需求"，是"做对一连串取舍"。**

**② AI 产品的核心工作，是把"模型的模糊能力"规定成"清晰的产品承诺"。**
传统软件的能力是确定的（点按钮就跳页）；AI 的能力是模糊的、有边界的、会在边缘失效的。所以 AI 产品最该被精确规定的，不是"有哪些功能"，而是：能力边界在哪（核心/边缘/界外）、每区该表现成什么样、什么算达标/越界、失败怎么归因改进——**这就是能力边界母表，它才是 AI 产品 PRD 的真正内核**。界面、流程、字段反而是外围。

**③ 能力边界的规定要尽早，它是一切的地基。**
测试、运营、prompt 把关全部建立在"先规定清楚能力边界"之上——母表是地基，其余是地基上的建筑。**规定完模型、写完交互就结束的 PRD，漏掉了 AI 产品最难、最核心的部分**。能力边界母表应与 PRD 同期甚至更早，而非项目中后期才补（补晚了，测试/运营/prompt 都被动）。

> 一句话收敛：**AI 产品的核心工作，是把"模型的模糊能力"规定成"清晰的产品承诺"——这个规定（能力边界）要尽早做、是一切测试/运营/prompt 的地基，且它的每一处都是 tradeoff，取舍的主体是 PM。**
