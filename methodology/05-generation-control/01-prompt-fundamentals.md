## 前提：prompt 工程之前先有"框架标准"

动手调 prompt 前，需要三件套：**成功定义 + 测试方法 + 初稿**，否则是盲目优化。
- **"成功标准"有两层**：框架标准（能力边界、各区期望、边缘处理）> 测试题（用例）。**框架是母、测试题是子，框架先行**。
- 框架标准（= 能力边界母表）的双重用途：① 指导 prompt 该写什么 ② 做把关 prompt 的标尺。**没有母表，prompt 把关无从谈起；有了它，把关就有了标尺。**
- 核心心法：**把写 prompt 当成给"绝顶聪明但对你项目零背景的新员工"下指令**——它不缺智力，缺你脑子里的业务背景和隐含预期。

## prompt 不是万能药：先归因，且要归到"哪一段 prompt"

- 不是每个失败都该用 prompt 解决。把关前先归因：是 prompt 问题，还是知识供给/系统问题？
- **归因维度不是"prompt vs 非prompt"，而是"哪个环节 / 哪一段 prompt"**：一个 agent 有多段 prompt——路由/意图识别（是一段 prompt）、匹配/检索、回复生成（另一段 prompt）——加上非 prompt 的知识供给、系统工程。
- **精确到"哪一段"，技术才不会改错地方**。

## 提示词技术阶梯（从最有效到最精细）

1. **清晰直接的指令**（最有效）：正向说"要什么"，给顺序步骤，具体到可执行。
2. **多示例**：给"输入→理想输出"，尤其放**边界/易混场景**的正负例。
3. **思维链（CoT）**：让模型先写推理再给结论。但增延迟成本；**新推理模型已内化 CoT，不必手动加**。
4. **XML 标签**：给 prompt 搭结构，让模型分清指令/背景/示例/用户输入。
5. **角色设定**：一句话调动一整套隐含行为的强力杠杆。但**只定大方向、定不了细节**。

## system prompt 该放什么 + 8 条把关清单

system prompt 放"全局稳定的身份和行为准则"。一个完整人设含五层：① 角色/身份 ② 能力声明（尤其"明确不做什么"）③ 行为规则（追问/兜底/语气）④ 红线（S0，显式）⑤ XML 结构化承载。

**8 条把关清单（技术给你一版 prompt，逐条核）：**
1. 角色：定了吗？调子对不对？
2. 能力声明：写了"能做什么"吗？尤其"明确不做什么"？
3. 追问逻辑：什么情况追问、追问什么，写清了吗？
4. 兜底逻辑：什么情况兜底、传达什么、后续动作，分类写清了吗？
5. 红线（S0）：绝不能做的，显式列出、在 system 层吗？
6. 具体可执行：每条规则，零背景新员工照做能不用猜吗？
7. 结构化：分块了吗（XML），还是糊成一坨？
8. 抗漂移：最关键的规则，放在显著位置、够突出吗？

## system prompt 的详略分寸

- **影响行为吗？** 影响行为的背景才放，纯介绍性的不放。
- **能不能变？** 不能变的写死、写具体；可以变的给"要点 + 示例"。
- **能直接执行吗？** 能→够了；要猜→写具体到能执行。

> 警惕反面：system prompt 不是越全越好。太长→关键规则被淹没；规则太多→互相冲突；话术锁太死→僵硬。目标是"写准"不是"写全"。
