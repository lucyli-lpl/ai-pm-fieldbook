---
title: Skill：场景化按需加载的 prompt
---

system prompt 承载的东西越多，"太长→关键规则被淹没；规则太多→互相冲突；话术锁太死→僵硬"就越难避免。根源在于 system prompt 是**全局常驻**的——每轮对话都完整加载，不管用户当前在什么场景。

Skill 是这个问题的解法：**把 prompt 体系从"一整坨 system prompt"升级为"system prompt（全局层）+ skill（场景层）"的两层结构。**

## Skill 的定义

Skill = **场景化按需加载的 prompt**。两个关键区别：

- **按需加载**：平时只占一行触发描述（几十 token），命中场景后才把完整指令加载进上下文。
- **场景化**：每个 skill 服务于一个具体场景，内部可以规定该场景的完整操作规程。

一句话：**system prompt 是"你是谁、全局怎么做"，skill 是"遇到这个场景、具体怎么做"。**

## Skill 与 MCP、Plugin 的区别

| | 解决什么问题 | 本质 | 例（服务台助手） |
|---|---|---|---|
| **Skill** | 模型有能力做，但不知道**按你的标准怎么做** | 场景化的操作规程（prompt） | "兜底回复的操作规程" |
| **MCP** | 模型**碰不到外部系统和数据** | 外部连接通道（工具调用协议） | 查 ITSM 获取流程入口 |
| **Plugin** | 需要把 skill + MCP + 命令**打包分发** | 分发和组合的壳 | 把服务台助手的全套能力打包复用 |

**判断口诀**：连不上外部系统 → MCP；知道该做什么但不知道按你的方式怎么做 → Skill；打包给别人用 → Plugin。

## 什么时候该用 Skill

**归因检查清单（逐条排除后，剩下的就是 skill 的活）：**

| 排除项 | 如果是，该改什么 |
|---|---|
| 模型连不上外部系统/数据 | → MCP |
| 流程走向需要编排 | → Workflow |
| 需要模型自主规划未知流程 | → Agent |
| 模型推理能力不够 | → CoT / 推理模型 |
| System prompt 里的全局规则本身写错或缺失 | → 改 system prompt |
| 知识库/数据缺内容 | → 补知识库 |

**以上都不是，但模型的执行质量仍然不稳定**：→ 这就是 skill 该做的事。

**典型信号**：
1. 同一场景每次执行方式不一致；
2. 某个场景的操作规程足够复杂，塞进 system prompt 会淹没其他规则；
3. 不同场景之间的规则互相干扰；
4. System prompt 改一处、别的场景表现漂移。

## System prompt vs Skill 的分工原则

**什么留在 system prompt**：角色身份、能力声明、全局判断规则、S0 红线、全局语气基调、Skill 索引。

**什么抽成 skill**：某个场景的完整操作规程、该场景下调什么工具、输出格式、语气和话术要点、边缘处理和降级方式。

**分工口诀**：system prompt 管"什么时候走这条路"（判断规则），skill 管"走上这条路后怎么走"（执行规程）。

## Skill 内部该写什么（结构）

1. **触发描述**（一句话，平时常驻于 system prompt 的 skill 索引中）
2. **前置条件**（可选）
3. **操作步骤**：按顺序规定该场景下的完整执行流程
4. **输出规范**
5. **分支处理**
6. **边界与禁止**
7. **语气与话术要点**

**设计原则**：
- 一个 skill 对应一个场景，不塞多个；
- Skill 内部的详略同样遵循"三把尺"——判断规则写死、话术给要点、能执行即可；
- Skill 可以规定工具调用顺序；
- 母表定义"该场景期望什么结果"（验收标准），skill 规定"该场景怎么执行才能达到那个结果"（操作手册）；
- Skill 不改变测试方法——仍然用母表的期望行为和 L1/L2 判定。
