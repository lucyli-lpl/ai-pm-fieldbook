---
title: 总览：两个阶段，一条循环（ADLC）
---

同一套能力边界（母表），驱动一个跨越发布的持续改进循环。业界称之为 ADLC（Agent Development Lifecycle）：**上线前测试 → 发布 → 上线后数据运营 → 反馈进下一版**。

```
        ┌─────────── 母表（单一事实源，共享轴心）───────────┐
        ↓                                                      ↓
  上线前：测试（5.1）                            上线后：数据运营（5.2）
  判定「够不够格发布」                            让数据驱动「持续爬坡」
  ─ 数据：预设/合成输入                           ─ 数据：真实用户流量
  ─ 目的：门禁                                    ─ 目的：发现与改进
  ─ 手段：断言(L1)/人工·LLM(L2)/A-B(L3)          ─ 方法：三源采集→打标→error analysis→派单
        └───────────→ 发布 ───────────→ 监控 ─────────┘
                                                （反馈进下一版）
```

**测试与数据运营的分界（三条重合的线）：**

| | 测试 | 数据运营 |
|---|---|---|
| 时机 | 上线前 | 上线后 |
| 数据 | 预设 / 合成输入 | 真实用户流量 |
| 目的 | 门禁（够不够格发布） | 爬坡（持续发现和改进） |
| 核心能力 | **判定质量**（评测手段 + 标准） | **数据流与归因**（数据源、关联、指标、归因） |

**关键区分：断言(L1)、人工/LLM 评测(L2)、A-B(L3) 是「测试」的手段（判定质量的工具），不是数据运营的工具。** 数据运营的核心不是"用什么评测手段"，而是"数据怎么来、怎么关联、怎么变成可归因的洞察"。两者只在末端交接：A-B（L3）用于验证运营循环中某次优化是否真的更好。

> 定位说明：AI 产品的质量不由"发布时"决定，而由"发布后的数据运营循环"决定——传统软件发布即巅峰（之后只修 bug），AI 产品发布是起点（之后靠数据爬坡）。因此数据运营方案与测试方案同等重要，是与 PRD 并列的核心资产。
>
> 数据运营部分的方法来源：Hamel/Shreya 的 error analysis（分析方法）+ OpenAI/Arize 反馈系统复盘（工程架构）+ 真实项目实践推导。因「AI 产品数据运营」这一领域尚无成熟公开方法论，此部分较多依赖实践假说，将随真实项目运营持续验证。
